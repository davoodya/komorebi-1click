# Handoff — installation-system repair (2026-10-10)

**Read this first if you are continuing this work.** It summarises the project,
the measured state, and the exact repair plan. The full evidence lives in
`AUDIT-2026-10-10-entry-points-and-config.md` (same folder).

---

## 1. What this project is

A portable, offline-first, one-click installer for a complete Windows tiling-WM
stack: **Komorebi 0.1.41 + WHKD 0.2.10 + YASB 2.0.7 + AutoHotkey v1 1.1.30.00
and v2 2.0.12** on Windows 10/11 x64. All six payloads are committed to the
repo with SHA256 pins; nothing is downloaded during install. After the binaries,
the installer generates the machine-specific configuration (monitors, whkdrc
with rewritten user paths, applications.json, YASB config), registers the
`Komorebi` logon task and `KomorebiWatchdog` task (both `RunLevel Highest`),
puts `komorebic.exe` on PATH, enables YASB autostart, and generates
`AppRunner.vbs` in the Startup folder for the three AutoHotkey scripts.

Repo layout (two trees, never mix):

| Tree | Role |
|---|---|
| `H:\Repo\komorebi-1click` (`/mnt/h/Repo/komorebi-1click`) | **publish** — the git repo, the only tree that ships. Work happens here. |
| `~/projects/komorebi-1click` (WSL) | **dev** — process docs, no git, does not build. |

Installer anatomy: `komorebi-1click-install.exe` (GUI wrapper,
`scripts/komorebi-install.cs`, ADR-0004 — escalates via UAC and forwards exit
codes) → `Install.ps1` (all logic) → `scripts/Install-Common.ps1` (the
library). Exit codes: 0 success; 1 primary/MSI failure or not-elevated;
2 configuration; 3 startup tasks; 4 AutoHotkey startup; 10 usable-but-
incomplete.

## 2. THE live-machine rule (mandated by Davood, 2026-10-10)

**Never** run the install/config scripts or anything that touches the live
Komorebi/WHKD/YASB/AutoHotkey stack or the machine's current configs on
DAVOIDPC. The stack is in a known-good state (verified: all processes running,
tasks Ready, installed `komorebi.exe` already the patched build). All testing
happens in **Windows Sandbox** (`sandbox.wsb`, `tests/start-sandbox.ps1`,
`tests/sandbox-verify-install.ps1`) or in **DryRun / temp-dir stub** form. This
rule is in Hermes memory and applies to every future session on this project.

## 3. Measured state (2026-10-10)

Both user-visible entry points are broken:

- **EXE** — *proven* to never launch the installer: `-SkipElevationCheck` is
  passed **before** `-File`, so PowerShell itself rejects it (exit 64 via
  pwsh 7; exit 1 via 5.1) and the GUI wrapper shows nothing. Reproduced
  end-to-end with a test-only build + stub installer.
- **Install.ps1** — script is healthy (full green run logged 2026-10-05, host +
  Sandbox), but every direct launch stops at the elevation gate because the
  account is a non-admin; a window that prints the report and closes reads as
  "nothing happened".

Plus two latent defects that bite on a **fresh** machine: the config generator
writes `app_specific_configuration_path` to a location it does not populate
(`komorebic check` does *not* catch it — verified), and the patched-komorebi
requirement is not implemented at all (the patch artifacts are also untracked
in git).

## 4. Repair plan (implementation phase, in this order)

1. **Fix the wrapper (`scripts/komorebi-install.cs`).** Move the switch after
   the script path: `-NoProfile -ExecutionPolicy Bypass -File "<installer>"
   -SkipElevationCheck [args]`. Parse-check, rebuild with
   `scripts/build-exe.ps1`, and **execute** the rebuilt EXE against a stub
   installer (stub in `%TEMP%`, elevation forced) requiring exit 0 and the stub
   to have run. Do not ship the rebuild without that execution proof.
2. **Fix the ASC path (`scripts/Install-Common.ps1`).** Stop rewriting
   `app_specific_configuration_path` in `New-KomorebiConfig` (keep the
   template's `%USERPROFILE%\.config\komorebi\applications.json`; komorebi
   expands `%USERPROFILE%` itself). Add a file-existence check to
   `Test-GeneratedConfig`/`Install-Configuration` so a missing ASC file fails
   the install loudly instead of crashing komorebi later.
3. **Commit the patch artifacts** (`docs/Access-Denied-Solving/`): patched
   binary + `.orig` + the fixing script + `patch_final2.py`. Decide with
   Davood whether the 14.6 MB patched binary ships in the repo (recommended:
   yes — the installer must not depend on untracked files).
4. **Add the patched-komorebi step to the installer** (new function, e.g.
   `Install-KomorebiPatch`, called right after the Komorebi MSI step): pin the
   SHA256 (`52b631cd…`), back up the installed `komorebi.exe`, copy the patched
   binary, verify the deployed file's hash and the two 6-byte patch sites
   (offsets `0x2898E9` / `0x28D7E4`). Idempotent: skip when the installed
   binary already matches. Also rename away any `komorebi.exe.manifest`
   (gate 2). Resolve all paths from `$RepoRoot` — **no hard-coded machine
   paths** (the existing fixing script's `H:\Repo\…` constants are this
   project's known anti-pattern for portable code).
5. **Tests that actually run things** (`tests/ticket09-exe-wrapper.tests.ps1`):
   build the wrapper, run it beside a stub installer, assert the stub ran and
   the switch bound; add the EXE entry point to the Sandbox suite. Keep the
   existing source-greps, but they are no longer sufficient.
6. **Sandbox verification of the whole installer** (the only place a real
   install may run): `tests\start-sandbox.ps1`, then run
   `tests\sandbox-verify-install.ps1` extended with (a) EXE double-click
   equivalent, (b) patched-komorebi hash assertion, (c) ASC-file existence.
   Record real exit codes in the handoff.
7. **Release plumbing (optional, for `irm | iex`):** publish a GitHub release
   containing `komorebi-1click.zip`; today that URL 404s.

Verification standard: report measured exit codes and outputs, never claimed
ones; the EXE rebuild is not "done" until the stub-run test passes; the patched
binary is not "deployed" until the deployed hash matches the pin.

## 5. Gotchas worth remembering before you touch anything

- **Windows PowerShell parsing:** after every `.ps1` edit, parse-check it
  (`[System.Management.Automation.Language.Parser]::ParseFile`); no line may
  start with a binary operator (`+ …` on a fresh line is a parse error).
- **`/init` interop mangles multi-argument Windows binaries.** Bare
  `/init exe arg arg` broke `komorebic check -k` and looked exactly like a
  komorebi defect (see audit H5). Always drive Windows binaries through
  `powershell.exe`/`pwsh.exe` + `Start-Process` with an `ArgumentList`, or
  `-Command`, so Windows assembles argv itself.
- **The installer requires elevation and the account is a non-admin** — the
  UAC credential prompt is expected; `ExitElevateRefused = 5` is the
  declined path.
- **`.gitignore` ignores `komorebi-1click-install.exe`** (build artifact) — it
  is regenerated by `build-exe.ps1`, never committed.
- The publish tree carries **pre-existing dirty entries** (modified configs,
  staged deletions, untracked backup dirs). Never `git commit -a`; always
  `git commit -F <msgfile> -- <explicit files>`, then `git show --stat HEAD`.
- All shipped text is **English**; the final report to Davood is **Persian**.
